# qwen3.7-max 元素记忆系统 A/B 测试报告

> 日期：2026-09-07
> 模型：qwen3.7-max（DashScope OpenAI 兼容端点）
> 用例：`cases/manhattan/login_and_query.yaml`（18 步，登录 + 充电订单查询 + 站点列表南京筛选）

## 1. 测试目的

量化「元素记忆系统」（查询注入 + auto_apply + auto_learn）对 **LLM token 消耗**的影响，并验证记忆系统在**正确性**与**成功率**上的价值，为「是否值得保留记忆系统」提供数据依据。

## 2. 测试方法

- **对照组 A（有记忆）**：`element_memory.enabled=true` + `auto_apply_enabled=true` + `auto_learn=true`
- **对照组 B（无记忆）**：上述三个开关全部关闭
- 同一模型、同一用例、同一平台，各运行 **3 次**，统计 token 用量与结果。

|------|-------------|--------|-----------|-------------|------|------|

| 3 | 254,842 | 243,070 | 11,772 | 17 | ✅ 成功 | — |

## 4. Token 对比分析

### 4.1 全量统计

| 指标 | 有记忆 | 无记忆 | 差异（无记忆省） |
|------|--------|--------|------------------|
| total 均值 | 276,971 | 234,539 | **42,432（15.3%）** |
| prompt 均值 | 261,282 | 221,099 | 40,183（15.4%） |
| completion 均值 | 15,689 | 13,440 | 2,249（14.3%） |
| invocations 均值 | 18.67 | 16.33 | 2.33 次 |

### 4.2 剔除异常值后（更稳健的中位数口径）

两组都各有一轮受「大 DOM 场景超时/截断」影响而异常（有记忆第 1 次、无记忆第 2 次），剔除后：

| 指标 | 有记忆（第2、3次） | 无记忆（第1、3次） | 差异 |
|------|--------------------|--------------------|------|
| total 中位数 | 254,842 | 227,926 | **26,916（10.6%）** |

> 说明：有记忆第 1 次的 325,652 是受「`max_completion_tokens=4096` 截断 bug」影响（该 bug 已在测试中途修复为 8192），属于异常值，不应计入记忆系统的真实开销。

### 4.3 关键结论：token 大头在 prompt，而非 completion 或记忆系统

**prompt 是绝对大头**：6 次运行中 prompt 占 total 的比例稳定在 **93.5%~95.4%**（有记忆 94.3% 均值、无记忆 94.2% 均值），completion 仅占 **4.6%~6.5%**。

- prompt 的绝对大头是**每步发送的全量 DOM 序列化**（站点列表 1171 条记录 + 订单 188 条记录），记忆命中提示注入只占几百 token（占比极小）。
- 记忆系统带来的 total 增量约 **10.6%**（中位数口径），主要来自「有记忆时 LLM 平均多 2 次调用」→ 多发送 2 份 DOM prompt，而非记忆文本本身。
- **auto_apply 本身不消耗 LLM token**（纯 JS 设值），auto_learn 是运行结束后的本地 JSON 写入，也不消耗 token。

**completion 指标解读**（模型输出量，衡量 LLM「纠结/尝试」程度）：

| completion 口径 | 有记忆 | 无记忆 | 差异 |
|-----------------|--------|--------|------|
| 全量均值 | 15,689 | 13,440 | 无记忆低 2,249（14.3%） |
| 全量中位数 | 14,061 | 13,632 | 无记忆低 429（3.1%） |

- completion 绝对值很小（1.1 万~2.1 万），只占 total 的 ~5%，且被「`max_completion_tokens` 截断 bug + 120s 超时重试」严重污染（有记忆第 1 次的 21,235 即为截断重试膨胀）。
- **数据方向与「无记忆 LLM 尝试多种方法 → 更费 token」的假设相反**：无记忆 completion 反而略低。但差异（0.9%~14.3%）在 3 次样本的噪声范围内，不具备统计意义。
- 结论：**completion 是「诊断指标」（判断模型是否在纠结），不是「成本指标」**。降本的正确杠杆是 prompt（占 93.5%~95.4%），而非 completion 或记忆开关。

## 5. 正确性与成功率对比

这是记忆系统价值的关键，比 token 更重要。

### 5.1 日期窗口正确性

| 场景 | 日期结果 | 是否正确 |
|------|---------|---------|
| 有记忆（auto_apply 开） | `08-28 ~ 09-06`（过去10天不含今天） | ✅ 正确 |
| 无记忆（auto_apply 关） | `09-01 ~ 09-07`（含今天，仅7天） | ❌ 错误 |

**关键证据**：无记忆时，LLM 在日志中**自己发现了日期不对**（`dates Sep 1 - Sep 7, covers only 7 days, not exactly past 10 days excluding today`），但因为任务文案写着「系统已自动设好勿改动」，它不敢改，只能带着错误日期继续——最终结论也把错误日期当成了「系统自动设定的正确值」。

这印证了 auto_apply 的核心价值：**用几乎为零的 token 成本，换来了日期这个关键业务条件的确定性正确**。

### 5.2 成功率

| 场景 | 成功率 | 说明 |
|------|--------|------|
| 有记忆 | **3/3（100%）** | 全部成功 |
| 无记忆 | **2/3（66.7%）** | 第 2 次用例2失败（城市筛选未生效） |

无记忆第 2 次失败过程：勾选「南京市」后，LLM 想「点其他地方关闭下拉」，结果点错了元素（点到无意义 span），紧接着 2 次 120s 超时，导致城市筛选未正确提交，查询结果混入其他城市（1171 条全量而非 145 条南京）。

## 6. 稳定性观察

两组都出现过 **120 秒 LLM 超时** 和 **输出截断**，这些与记忆开关无关，是 **qwen3.7-max 在大 DOM 场景下生成慢**的模型特性问题：

- 有记忆第 1 次：`ModelOutputTruncatedError`（4096）+ 120s 超时
- 无记忆第 2 次：2 次 120s 超时

这些异常集中在「城市级联面板展开 + 站点列表 1171 条记录」的大 DOM 场景。

## 7. 结论

1. **记忆系统的 token 开销约 10%**（中位数口径），不是主要成本；token 大头是 DOM 序列化，与记忆无关。

2. **记忆系统的收益远大于成本**：
   - 日期正确性：有记忆 ✅ / 无记忆 ❌（auto_apply 用零 token 换确定性）
   - 成功率：有记忆 100% / 无记忆 66.7%

3. **记忆系统不是 token 负担，而是「花小钱办大事」**——用约 10% 的 token 换来了日期正确性和更高的成功率。

4. **若想省 token，正确方向是裁剪 DOM**，而不是关闭记忆系统。browser-use 0.13.10 暂无 DOM 元素数量上限参数，`include_attributes` 默认已精简（不含 class），裁剪空间有限，需从用例设计层面（如操作前收起不必要的面板）入手。

## 8. 建议

1. **保留并继续启用记忆系统**（三个开关保持 `true`）——它的价值在正确性（日期 100% 正确）与成功率（100% vs 66.7%），而非 token。
2. **降本第一杠杆 = 优化 prompt**（占 total 的 93.5%~95.4%），具体方向按收益排序：
   - **裁剪 DOM**（最大头）：站点列表 1171 条 / 订单 188 条是主要来源；
   - **压缩历史**：`max_history_items` 限制注入上下文的历史消息数；
   - **减少无效交互步**：`max_actions_per_step` 调低，减少无效交互带来的额外调用；
   - **精简系统提示与工具定义**：`follow_memory` 等工具定义、记忆命中提示文本的瘦身。
3. completion 优化收益极低（仅占 ~5%），不应作为降本重点。

- browser-use 版本：0.13.10
